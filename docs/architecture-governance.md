# Tuyile 架构专项治理

日期：2026-10-29。审阅基线：M2 提交 `a1acb8c`。状态：G1—G6 已随 M3 五步完成并通过自查与独立 review；M4 本地技术验收尚未开始。本文件记录当前必须处理的结构问题和验收要求，不把设计完成视为实现完成。

## 1. 目标与适用范围

短期收敛功能，长期保留变化空间。项目尚未上线，无需为生产兼容维持双实现；但现有本地数据、已交付行为和旧项目隔离仍须保护，不能以未上线为由清库或覆盖旧服务。

保持 TypeScript 模块化单体、React/Vite/Ant Design、Hono、PostgreSQL、一个 Worker、HTTP 轮询和私有图片卷。此次治理集中于即将随画布、Agent 和图库增长的业务边界，不更换技术栈，不建设通用平台。

文档分工：业务以 [产品基线](product-baseline.md) 为准，整体技术边界见 [架构设计](architecture.md)，本文件规定治理差距、最低实现和验收；交付仍遵循 [工程执行计划](exec-plans/active/tuyile-foundation.md) 和 [路线图](delivery-roadmap.md)。治理作为 M3 内部前置及集成工作，不新增里程碑、不拆分阶段提交。原文档轮次已结束；当前 M3 按工程执行计划第 14 节的五步提交与逐次 review 安排推进。

## 2. 本轮已确认的业务决定

### 2.1 图片额度与上游成本分开

- 图片额度只计算成功且本地持久化的图片，包括中间基准图；后续用户删除原图不返还已用次数。
- 上游已调用但未得到本地成功输出，不直接扣图片次数；调用尝试与能够获得的费用证据单独记录。费用未知继续标 unknown，不猜测账单。
- 未知结果暂时保留对应图片预留和必要引用，人工核验确认无法取得图片后释放预留。管理员仅查看元数据与结算证据，不获得私人图片或提示词权限。
- 人工声明“上游成功/收费”不能凭空增加本地输出或图片已用次数。成功计次必须关联经过验证的本地持久化输出；人工处置及晚到证据不得造成重复结算或覆盖已完成处置，不新增自动恢复模型执行能力。
- Agent 规划仍在首次上游调用前提交一次计次，开始后失败不返还；它与图片成功计次的规则不同。

### 2.2 规划与图片服务分别配置

允许规划服务和图片服务使用不同服务商；首版每类一个当前有效配置，普通用户只能选择管理员允许的模型。任务引用不可变配置版本，旧版本不因切换当前配置立即消失。暂不做同类多供应商路由、自动切换和比价，未知调用不得通过换服务重发。

### 2.3 技能与工具可注册、可组合、可停用

技能表达创作方法，工具提供实际执行能力。首版由管理员管理声明式技能，由开发者实现并在部署时注册可信工具；未来可按需求扩展第三方插件能力。

技能可以指导澄清、规划和组合工具，不能扩大权限、改变费用规则或绕过用户确认。普通停用阻止新计划使用；紧急撤销阻止后续尚未发出的相关调用，在途调用仍只能尽力取消。已确认计划绑定技能及工具定义版本，不随编辑而改变执行含义。

## 4. 治理规格与验收

### G1：应用用例掌握规则与事务

在现有 core/infrastructure 包内按 identity、projects、creation、assets、quota、providers、skills/tools 等实际职责组织模块，避免每实体一个包。入口只组合依赖并调用授权用例/查询服务，不能取得公开的全能 repository。纯查询可直接使用专用 SQL 查询适配器，但必须经过授权查询边界。

应用用例负责业务校验、事务编排和状态决定；领域规则尽量为可独立验证的函数；适配器负责 SQL、文件和外部协议。仓储可以提供语义明确的条件更新，不要求将 SQL 细节拆成机械 CRUD 调用。DB 行类型和服务端执行配置有明确类型，不用 any 穿过模块接口；contracts 中的管理输入与服务端秘密配置分开。

跨模块用例使用同一事务上下文：确认计划时任务、预留和参考图引用一起提交，写输出时资产 ready、输出记录与额度结算一起提交。网络、解码和文件操作在数据库事务外执行，保留写入意图和失败清理，不宣称数据库/文件共同事务。

**验收：** API/Worker 无绕过业务用例的写路径；关键领域规则可独立测试；真实 PG 故障注入证明上述跨模块操作全部回滚或全部提交；依赖检查阻止 core 引入 Hono、pg 或前端模块，web 不引入服务端配置。无需 DI 容器、领域事件总线或每表一套抽象。

### G2：任务、输出、资产和额度各自承担单一业务含义

建立以下最低模型，具体表名在实现时确定，不能仅通过改名完成治理：

| 概念 | 必须表达的关系与不变量 |
| --- | --- |
| 任务 / 确认计划 | 归属、幂等身份、不可变确认输入、配置/技能/工具版本；只支持实际需要的图片、规划和计划执行类型 |
| 执行步骤 / 调用尝试 | 顺序依赖、dispatch 分界、明确/未知结果、尝试预算；重启不续跑旧 running 步骤 |
| 输出 | 稳定 output ID、步骤与资产关联；删除资产后仍可保留必要追溯信息，不能把资产存在等同于任务成功 |
| 资产 | 独立工作区归属、文件状态与容量；可跨本人项目复用；不因源项目删除而级联删除 |
| 活动引用 | 任务、画布、对话、计划、收藏等实际引用源，workspace 复合约束；追溯关系与阻止删除的活动引用分开 |
| 额度预留 / 流水 / 汇总 | 业务来源、类型、归属日、预留/消费/释放及核验记录；唯一来源防重复，汇总与流水同事务维护 |

图片已用数、已保存输出数、上游尝试数和费用证据分别展示、命名和计算。修正当前 resolve 无本地图片却增加 used 的路径，同时修正管理 DTO、页面文案及旧测试期待。保留每日汇总用于准入；提供流水与汇总核对，不建设复式记账、支付账本或事件溯源。

保留跨日预留、当日实际尝试限制、整计划预留及文件安全发布规则。项目删除允许清除项目正文及活动引用，保留图库原件和必要脱敏审计；具体外键删除策略必须覆盖这些语义，不能依靠整个任务/资产链级联删除。

**验收：** 无本地成功输出不得新增图片消费；上游收费但无本地图片的核验只释放相应图片预留并保留调用证据；部分输出、跨日、重复回执、重复核验、晚到结果不会重扣或重复释放；汇总可与明细核对。项目删除保留资产，跨项目复用不扣生图次数；原图删除不返还历史次数；所有引用/删除与权限反例通过真实 PG 验证。

### G3：读取不参与全局写串行化

将授权查询与写事务拆开。任务/资产/额度读取不取创作全局 advisory lock、不使用无必要的用户 FOR UPDATE、不创建额度行；缺省额度用只读结果表达，初始化在账号建立或受控写操作完成。多表快照按需要用单条查询或短只读事务保持一致性，不降低 workspace 鉴权。

列表输出批量读取，查询数不随列表行数逐条增长。写操作针对真实竞争对象互斥；全局队列容量可保留短准入锁，Worker 单实例 session 锁继续保留，两者与普通查询分开。

在移除全局写锁前列出所有写用例的锁对象和统一获取顺序，覆盖身份撤销、任务准入/领取/dispatch、结算、核验、引用变化及删除。必要的对象 ID 预读后在取得锁时重查状态，不能使用锁前快照决定授权。跨模块共享同一锁协议，不能仅改某一个仓储方法。

**验收：** 真实 PG 双连接测试证明持有写准入锁时无关用户的任务/额度/图片读取可完成；查询不写业务表，列表查询次数有固定上界。重跑并发超额、队列容量、撤销与 dispatch、删除与引用、核验与晚到结果竞争测试，保证不超发、不重扣、无悬空引用。无需读副本、Redis 缓存或复杂 CQRS 基础设施。

### G4：服务端状态、编辑文档和临时交互分离

建立显式客户端路由和统一会话处理；采用成熟的查询管理能力处理缓存、取消、失效、轮询和请求去重，具体库随实现核定，不再让每个页面自行实现一套请求生命周期。

- 服务端状态：任务、项目、资产、额度、计划。缓存身份含当前账号/工作区/项目，退出或切账号清除，慢响应不能重新写入旧身份数据。
- 项目编辑状态：自有版本化 CanvasDocument、选区、撤销栈、revision、保存队列和冲突状态，每项目独立。React Flow 只作为显示与交互适配层，不直接持久化其完整运行时对象。
- 临时状态：表单、弹窗、上传进度等留在功能组件。标准控件继续由 Ant Design 提供，不重建控件系统。

保存串行化，异步结果绑定 workspace/project/epoch；切页、关闭编辑上下文和主动注销遵守保存/冲突恢复流程。会话已撤销时不得以保存为由继续展示旧用户私有状态。未经用户授权，不新增浏览器持久存储私人正文的离线草稿系统。

任务输出落图通过稳定 output ID 和随文档保存的 placement receipts 处理，轮询不能覆盖本地几何编辑；移除节点不移除“已经处理过该输出”的事实。提交结果不明时保留原幂等身份并查询，刷新不能自动新建任务。轮询仅覆盖需要更新的数据，允许页面隐藏时暂停读取，恢复后补查；这不取消后台执行。

按页面边界加载代码，避免账号管理和完整画布始终进入同一个初始包。现有主包大小提示属于随结构调整处理的非阻断优化，不设脱离实际页面的任意体积目标。

**验收：** 中大型桌面真实浏览器覆盖快速项目切换、旧请求延迟返回、跨标签账号切换、保存冲突保留、退出失败恢复、重复轮询不重复落图、删除节点不复活、刷新不新发调用；画布拖动/撤销不产生模型请求。保留 A 布局/B 窄轨，不新增手机专项交付、实时协作或 CRDT。

### G5：模型协议在能力边界内变化

分离管理输入（如 preserveKey）、仅服务端可见的执行配置和普通用户可见的能力描述。规划与图片服务分别管理当前版本；规划接口与图片接口独立，凭据不进入任务明文、浏览器 DTO 或日志。

能力至少描述当前业务实际需要的生成/参考图编辑支持、参考图上限、尺寸、质量和输出格式。有效请求范围为“产品支持 ∩ 模型能力 ∩ 用户策略”；前端据此给出有效选项，后端在准入和调用前验证。已确认输入遇到撤销或不兼容时明确失败，不静默降质或替换版本。

Provider 负责协议转换、受限响应和错误分类；业务层统一决定重试、预算、deadline 和取消。只实现已选择的协议，通过受控响应与 fake 测试，不宣称真实服务兼容性已验证。

**验收：** 两类服务可独立配置且互不覆盖；不支持的规格在调用前被拒绝；切换当前配置不改变旧确认计划；撤销阻止后续 dispatch；管理输入与执行密钥不泄漏；未知响应不自动重试或换服务。真实模型烟测仍需模型、次数和费用授权。

### G6：建立轻量技能与工具注册契约

采用固定 registry 和类型化执行接口，不加载任意上传代码，不使用运行时包安装或脚本解释器。

| 扩展 | 首版最小定义 | 管理与使用 |
| --- | --- | --- |
| Skill | 稳定 ID、不可变版本、名称/说明、创作指导、适用场景、所需输入与工具依赖 | 管理员注册/编辑新版本/启停；Agent 用于澄清和规划 |
| Tool | 稳定 ID、定义版本、输入/输出 schema、所需权限、外部访问及费用/资产副作用声明、执行实现 | 开发者提供可信实现，部署入口注册；Worker 经统一执行用例调用 |

工具声明接受平台校验，不能让插件自行定义扣额时机或授予自身权限。执行上下文仅提供已授权范围内的能力，不能把无边界数据库连接和全部 Provider Key 交给工具。首版只注册现有生成/参考图编辑等实际工具，不为证明接口而新增收费产品功能。

技能启用时检查依赖，规划和确认时检查版本/输入/能力，dispatch 前复核权限、撤销和预算。确认计划保存实际使用的技能版本、工具定义版本及服务配置版本。工具版本缺失或不兼容时明确拒绝执行，不拿最新实现冒充旧版本；有未结束任务引用的版本不能直接移除。支持新版本不等于承诺所有未来版本永久兼容。

普通停用阻止新的规划/确认使用，既有已确认任务仍按绑定版本执行；紧急撤销阻止后续调用，并对在途尽力取消。依赖不可用的技能不得继续产生可确认的无效计划。技能文本是指导数据，不能通过指令覆盖授权、确认、额度或工具白名单。

**验收：** 用无付费调用的合成技能/测试工具验证注册、重复 ID/版本冲突、输入输出校验、依赖缺失、版本锁定、普通停用、紧急撤销与未授权工具拒绝。增加测试工具只需新增实现与注册，并复用既有执行/结算流程；不改队列核心。测试注册不进入生产能力清单，不新增抠图等首版外产品功能。

## 5. 执行依赖与范围控制

**交付节奏更新：** 用户最新明确采用五步、五次提交，每次提交后由一个 sub-agent review；以工程执行计划第 14 节为准。此要求覆盖本文早先 M3 不拆提交及不召唤 sub-agent 的安排；主代理亲自实施、修复，审阅不代写。下面保留技术依赖顺序，提交边界按最新五步执行。

1. 先在同一 M3 工作中完成 G1 的用例/事务接口及 G2 的数据和结算语义，补齐迁移方案；明确每个跨模块动作的原子边界。
2. 在上述边界下实施 G3，先写锁协议和竞争场景，再缩小锁范围；不能先删锁再依赖普通功能测试证明正确。
