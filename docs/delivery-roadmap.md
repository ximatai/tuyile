日期：2026-10-29。状态：阶段 1—2 完成，阶段 3 进行中，阶段 4 尚未开始。

> 2026-10-30 最新范围覆盖历史迁移安排：用户确认无旧数据迁移需求，M4 只完成本地运行/发布技术就绪及合成备份恢复，不做 SQLite 导入、旧内容转换、归属映射或真实迁移。详见工程计划第 19 节。关键页面效果图校准及最终本地端到端验收仍为交付要求。

## 1. 目标与文档分工

首版交付指定用户可使用的私有图片创作工作台：登录并创建项目，提交图片或确认 Agent 计划，后台独立排队执行，返回页面查看作品并继续创作。

[产品基线](product-baseline.md) 是业务范围来源，[架构设计](architecture.md) 是技术边界来源，[工程执行计划](exec-plans/active/tuyile-foundation.md) 规定每阶段实现范围与详细验收。本文件只组织开发顺序、可演示成果、里程碑、决策时点和进度报告；不另建一套业务规则或小阶段。

以验收结果驱动交付，不预设未经验证的日历工期。用户已确认没有硬性首版上线日期，先按验收推进。阶段 1 完成后，用实际实现、测试、review 和返修耗时估算后续日期；以后每阶段完成更新一次预测。若用户给出硬期限，明确讨论范围、资源或日期的取舍，不通过跳过隔离与验收压缩工期。

## 2. 开发顺序与完整阶段

开发依赖为：M0 文档基线 → M1 账号与项目 → M2 后台创作 → M3 完整工作台 → M4 迁移与发布就绪。每个实现阶段只对应一个完整交付和一次提交；阶段内实现顺序不形成子阶段或额外提交。实现由主代理亲自完成，独立 reviewer 只承担提交后的验证。

**M3 最新例外：** 用户已明确将后端治理、扩展机制、画布与前端基础、完整创作功能、整体验收与交付拆为五次提交，每次提交后召唤一个 sub-agent review。主代理亲自实现及修复，review 问题 amend 到对应提交，通过后进入下一步；详细范围和状态见工程执行计划第 14 节。本例外覆盖本文件有关 M3 不拆提交的旧安排，不改变 M3 总范围或 M4。

M2 后形成 [架构专项治理](architecture-governance.md)：用例/事务、数据与额度、读写锁、前端状态、服务能力、技能/工具注册六项进入实施，尚未完成专项验收，作为 M3 内部前置及集成工作，不另拆里程碑。M3 需同时通过专项验收和原有完整工作台验收；治理文档不表示 M3 完成；当前实施记录见工程执行计划第 13 节。

| 阶段 / 里程碑 | 开发重点与涉及模块 | 完成后可演示的结果 | 进入条件 |

| 阶段 2 / M2：后台创作闭环 | 任务/调用/额度/资产 schema；单 Worker、有界队列、Provider 适配、状态轮询、最小创作与管理对账入口 | 提交假 Provider 生图或参考图任务 → 关页/普通注销 → 重新登录查看结果、额度与私有原图；中断失败可解释 | M1 完成 |

M3 表示已确认功能在隔离环境完整可用；M4 表示迁移工具和发布材料通过技术验收。二者都不等于真实旧数据已迁移、真实模型已验证或生产已上线。

## 4. 每阶段固定交付节奏

1. 核对上一里程碑、工作区和隔离环境，按工程计划完整实现本阶段；保留原有未提交内容。
2. 完成该阶段必要类型、构建、PG、浏览器及 Docker 检查，整理可演示成果和待授权外部事项。
3. 统一提交一次，主代理对该提交自查并修复；修复 amend 到同一提交。
4. 召唤一次独立 reviewer，独立上下文只读检查本阶段提交并运行相关验证，不代写实现。若失败，由主代理修复，再由同一个 reviewer 在 fresh 上下文复验受影响项；不增加第二个 reviewer。
5. 检查通过后更新里程碑状态和验证摘要，amend 到该阶段提交，报告成果、提交号、风险和下一完整阶段。

里程碑完成必须同时具备完整范围、验收通过、自查完成和独立验证通过。代码已写完、已经提交或 UI 已演示都不能单独作为完成依据。后续若发现回归，登记问题并修复，不用历史通过记录替代当前验证。
